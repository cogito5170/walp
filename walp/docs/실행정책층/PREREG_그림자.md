# 사전등록 — P1~P3 그림자 모드 (V1)

수를 보기 **전에** 커밋한다. 그림자 모드: 정책은 **제안만** 하고 실제 행동은 LLM 이 한다. 둘을 맞대어 정책이 맞았는지,
켰다면 몇 턴 · 몇 토큰을 아꼈을지 잰다. 아무것도 막지 않는다.

## 정책(`walp/execpolicy.py`)

| | 방아쇠 | 제안 |
|---|---|---|
| **P1 같은 상태 재사용** | 사람 · 훅의 말이 **이전에 받은 말과 같고**(정규화 해시), 그 저장소의 **상태 해시가 그때 턴이 끝났을 때와 같다** | 이전 결론을 다시 낸다(LLM 안 부름) |
| **P2 발행 매크로** | `git commit` | `walp-exec publish` 한 번: 깨끗한 워크트리 검사 → 밀기 → PR → 머지 → 머지 확인 |
| **P3 기다리기 이벤트** | 기다리는 명령(`kill -0` · `sleep` · 같은 프로세스 확인)이 든 턴 | `walp-exec wait` 한 번: 끝날 때까지 막고 요약 한 줄 |

상태 해시 = 그 저장소의 HEAD · 브랜치 · 원격 추적 ref · 작업 트리 변경 목록(`git status --porcelain`)의 해시.

## 맞음(일치)의 정의 — 미리 고정

- **P1**: 제안 뒤 실제 턴들이 그 저장소의 상태를 **안 바꾸고** 끝났다 → 맞음(재사용했어도 상태로는 같은 결과).
  바꿨다 → 틀림(재사용했으면 할 일을 빼먹었다). *한계: 상태가 같아도 답의 내용이 달라야 했을 수 있다 — 상태로만 본다*
- **P2**: commit 뒤 **12 턴 안에** 밀기와 (PR 만들기 또는 머지)가 다 있고, 그 사이에 파일 고치기가 **없다** → 맞음.
  사이에 고치기가 있다 → '멈추고 올림'(매크로는 검사 실패에서 멈추고 LLM 으로 넘겼을 것). 밀기가 없다 → 틀림(발행하지 않을 커밋이었다)
- **P3**: 기다리는 턴이 연달아 k 개(k≥2) → 맞음, 아낀 턴 k−1. 하나뿐이면 아낀 것 0(제안은 했지만 턴이 같다)

## 아낀 것의 정의

- 아낀 턴: P1 = 맞은 제안 뒤 다음 사람 말까지의 모형 턴 전부 · P2 = commit 턴 다음부터 마지막 발행 걸음까지의 턴 − 0(매크로 호출은 commit
  턴 자리에서 한 번) · P3 = k−1
- 아낀 토큰: 그 턴들의 실제 토큰 합(추적의 usage). **상한**이다 — 매크로가 돌려주는 요약 한 줄이 다음 턴의 맥락에 더해지는 몫은 빼지 않았다
- 틀린 제안의 비용은 따로 센다 — 켰다면 사람이 다시 말하게 했을 횟수

## 어디서 재나

1. **오프라인 재생** — 이 세션 주 추적(1,454 턴)과 하위 에이전트 추적. 추적에는 저장소 상태가 없으므로 P1 의 상태 해시를 **대리**로 잰다:
   "그 저장소를 바꾸는 도구 호출(파일 쓰기 · git commit/push/reset/merge/checkout)이 그 사이에 있었나". 대상 저장소는 명령의
   첫 `cd` 또는 파일 경로로 정한다(없으면 세션 cwd)
2. **실제 그림자** — 정책을 Claude Code 훅(UserPromptSubmit · PostToolUse · Stop)으로 걸고, 진짜 `claude -p` 세션이 임시 저장소에서
   일하게 한다. 원장(`~/.walp/shadow.jsonl`)에는 **해시 · 종류 · 수만** 적는다(글 · 명령은 안 적는다). 여기서는 상태 해시를 진짜로 잰다

## 결정 규칙

켜기 후보가 되려면(V2 봉인 A/B 로 넘어가려면): 그 정책의 제안 ≥ 10 개, 일치율 ≥ 90%, 틀림(P1 의 상태 바꿈 · P2 의 밀기 없음) ≤ 5%.
제안이 10 개가 안 되면 "잴 만큼 안 나왔다" 로 적는다.

## 사소한 설명 — 재서 죽일 것

1. 아낀 토큰이 맥락 크기 탓만 — 아낀 **턴 수**를 같이 적는다
2. 이 세션의 일 섞임 탓 — 하위 에이전트 추적과 실제 그림자 세션을 따로 적는다
3. 대리 상태(P1 재생)가 틀림 — 실제 그림자에서 진짜 해시로 같은 정책을 다시 잰다

### 읽는 법 — 사소한 설명을 재서 본 것

- **P1 의 틀림 18 중 17 은 대리 상태의 거짓 양성이다.** stop 훅 말 뒤에 내가 원격이 없는 갈래로 `git push` 를 다시 **시도**했고,
  대리는 시도를 상태 바꿈으로 셌다. 실제로는 다 실패했다 — 훅의 말이 매번 같은 "65 unpushed" 였다(상태가 안 바뀐 증거).
  진짜 상태 해시로 잰 실제 그림자에서는 2/2 맞음. 그러나 2 개뿐이라 이것으로 P1 을 켤 수는 없다
- **P2 는 방아쇠가 틀렸다.** 이 세션의 commit 은 사전등록 커밋 · 중간 저장이 많았고, 밀기와 PR 사이가 12 턴을 넘기 일쑤였다.
  사후(가설 아님): 방아쇠를 push 로 바꿔도 19%(88 중 17). **"commit/push 뒤에는 발행이 따른다" 는 이 사용에서 성립하지 않는다**
  → P2 는 정책이 스스로 켜는 것이 아니라 **LLM 이 부르는 매크로 도구**여야 한다(발행할 때를 LLM 이 정하고, 걸음은 매크로가)
- **P3 의 100% 는 정의상 거의 참이다** — 기다리는 턴이 연달아 있으면 맞음으로 셌다. 잰 것은 "아낀 턴 80" 이지 정책이 옳다는 것이 아니다.
  재지 않은 위험: 폴링 중간에 내가 사람에게 진행 상황을 알렸다 — 끝날 때 한 번만 돌려주면 그 중간 보고를 잃는다
- 실제 그림자에서 찾은 결함: 'git commit && git push' 를 한 호출로 하면 실시간 보고가 밀기를 못 봤다 → 고쳤다(검사가 고치기 전 코드에서 실패)
- 한계: 중첩 실행이라 다섯 세션이 이 세션의 session_id 를 물려받았다(추적 파일 하나에 차례로 쌓여 시각으로 갈랐다)
